## In flight — PR #10, NOT merged (branch `fix/jwks-refetch-throttle`)

A security review found a **HIGH** at the owner door: `JwksKeyResolver.get()` refetched the JWKS on **every** unknown `kid` — and the `kid` comes from the *unverified* token header, so an anonymous flood of random-`kid` tokens forced one outbound fetch per request (thread-pool saturation + flooding the upstream JWKS endpoint).

**The fix** (`e881d8e`): a refresh cooldown (default 300s, a `Settings` field), a bounded negative cache for unknown `kid`s, attempt-based throttling (stamped *before* the fetch so a hanging upstream is throttled too), an injectable monotonic clock for deterministic tests. Still fails closed; a genuinely rotated key is picked up on the first miss after the cooldown. Plus defense-in-depth (`c8c8dfa`): an owner-door body-size cap scoped to `/v1/tenants` so the future upload path isn't throttled.

**Then the reviews worked the fix itself over — 12 more commits, each a caught issue:**
- Crafted `Content-Length` caused a 500 at the owner body cap (`188e717`) and the same bug existed at the visitor gate (`e48d018`); the shared cap logic was then extracted once (`f8baf99`).
- JWKS fetch failure surfaced as an unhandled 500 → converted to a clean 503 (`e8f03e5`), with the upstream failure cause logged (`22c8fcf`).
- The resolver's miss path wasn't thread-safe → locked (`1dc0844`).
- Gate path prefixes matched with bare `startswith` → segment-boundary matching (`171fef4`); the body-cap prefix and the cooldown default were single-sourced (`e540e70`, `b97436d`).
- Deferred hardening and accepted limitations written down in `docs/FOLLOWUPS.md` (`328c534`), incl. that the body cap checks the *declared* Content-Length only (`3bad459`).
