# Step 1 (Day 1), explained plainly

## The idea of the whole day

By the end of Day 1 you want the auth spine standing: the three ways anything ever enters the system, each proven and tested, on top of the already-primed scaffold. Those three are the owner login (a real Supabase JWT, the only login), the visitor widget gate (a public key plus an allowed-domain check, no login), and a working, secured MCP server (Model Context Protocol, a standard way for external AI tools to call tools on your server) that you have proven is callable with an external-caller token. The reason all three go on the same day is deliberate. The auth spine is the foundation everything later sits on, and the MCP server is the single scariest piece of the whole build, so you prove it works now, while there is still room to change course if it fights you. Naming the three callers separately in code on day one is also what stops them from quietly collapsing into one another later.

## What happens, in the order you would actually do it

(Steps 1 to 3 below are already DONE: Milestone 0 priming created the repo, the tooling, the typed FastAPI scaffold, the CI quick-gate, and the local Supabase plus Weaviate stack. They are kept here for the full picture. Day 1's real work starts at the auth spine, step 4 onward.)

1. **Create the repo and set up the project.** (Repo is short for repository, the code project tracked by git and hosted on GitHub.) You lay down the folder structure, the Python tooling, typed code, and tests sitting next to the code. This is first because everything lives here, and you set the quality floor from the very first commit rather than trying to add it later.

2. **Stand up a CI skeleton.** (CI is continuous integration, an automated pipeline that runs your tests every time you push code, so breakage shows up immediately instead of days later.) It does not run the AI evaluation checks yet, that comes on Day 7. For now it just runs tests, so a green build means something real from day one.

3. **Build the FastAPI service.** (FastAPI is a Python framework for building web APIs, in plain terms the backend server that the widget, the dashboard, and the agent will all talk to.) You create its typed surface now. This same service will later also hold the agent and the document-ingestion worker, so it is the spine you are putting in place.

4. **Wire up backend-for-frontend secret handling.** (Backend-for-frontend means the browser only ever talks to your own server, and your server is the one that holds the secret keys and talks to the AI. The keys never get sent to the browser, where anyone could read them.) You bake this in on day one on purpose, because a secret key sitting in browser code is effectively shared with every visitor and attacker.

5. **Set up Supabase auth so it issues JWTs for the OWNER login path only.** (Supabase is a hosted service that gives you a Postgres database and user login out of the box. A JWT, JSON Web Token, is a small signed token that proves who a logged-in user is.) This is the only real login in the whole system, and it gates the owner's document upload and ingestion. Note this token is for the owner, not for the visitor and not for the MCP caller, those are different people in different trust domains (see the next two steps).

6. **Build the visitor widget-key gate as its own first-class piece.** The widget installed on the owner's public website is used by visitors who never log in, so there is no JWT here. Instead the widget carries a public widget key (a key that sits in the page source, so it is NOT a secret, anyone can read it). The gate checks it in layers: the key exists in a valid-keys store, the request Origin/Referer (the header the browser stamps to say which site the request came from) is on that specific key's allowed-domain allowlist, a per-key and per-IP rate limit applies, then the request is sanitized down to just the query before it reaches the core. The Origin allowlist is a deterrent (a non-browser client can spoof it), so the load-bearing protections are the narrow scope, the rate limit, and grounding plus injection screening. On Day 1 you build the key check, the Origin allowlist, and the sanitize fully, and stub the rate limiter behind a clean interface (the real limiter comes on Day 11).

7. **Do the MCP spike (the main event of the day).** You stand up a remote MCP server (remote meaning it runs as a web service reachable over the internet, not just on your laptop) using Streamable-HTTP (the modern way an MCP server communicates over ordinary web requests). It listens on one endpoint (a single URL path the server answers on, here `/mcp`). The MCP is a separate door for EXTERNAL AI callers (for example a customer wiring your assistant into ChatGPT or their own agent), not the owner login and not the visitor widget. So you secure it as an OAuth 2.1 Resource Server (a server that only validates tokens and serves the tool, leaving the issuing of tokens to a separate authorization server). You demonstrate ONE correct check end to end: validate the inbound external-caller token (its signature, issuer, audience equal to this server, and expiry), reject anything not issued for this server, validate the Origin header (reject with 403 when it is present but not allowed), and never pass the inbound token upstream. This token is an external-caller token (on Day 1, a self-minted scoped API key that you mint and validate yourself, which is free and fully in your control), explicitly NOT the owner's Supabase JWT. Then you expose the answer-with-verdict capability as the tool, through a thin adapter over a stubbed core, and confirm an MCP client (the thing that calls the server, for example Claude Code) can both see the tool and call it through the secured endpoint.

8. **The core capabilities are plain functions, exposed two ways.** The real work (`retrieve`, and `answer` which returns the answer fused with an honesty verdict) lives as ordinary typed functions. Two thin adapters wrap that one core: the in-process call the visitor gate uses, and the MCP tool the external caller uses. Same logic underneath, no duplication, and each surface resolves its own tenant at its edge (widget key for the visitor, token for the MCP caller) before calling the core. On Day 1 the core is a stub returning typed placeholder shapes; real retrieval is Day 5 and real grounding/refusal is Day 6.

## What you have at the end of Day 1

The three auth paths stand and are tested: the owner Supabase JWT is verified on the login/ingestion routes, the visitor widget-key gate accepts an allowed key from an allowed domain and rejects the rest, and an MCP client successfully lists and calls your secured remote tool using an external-caller token (with bad origins and bad tokens refused). The core behind all three is still a typed stub. CI is green across all three paths. That is the proof, an actual working spine, not a checkbox.

## Why this is Step 1

The authentication on the MCP server is the single biggest schedule risk in the whole project. The protocol's security spec is genuinely complex, it stacks several separate web-security standards, and a real engineering team spent about two weeks just understanding it before throwing away their first attempt and starting over. If you left it to the end, you could discover late that it is harder than expected, with every other part of the system already built on top of it, and the whole flagship would slip. So you prove the scoped version on day one instead. If it is going to bite, it bites now, while there is still time to adjust, rather than in the final week. That is the same reasoning that puts the other scary pieces (bad PDF files, a flaky evaluation gate, prompt injection) early in the plan too: surface the risks while you can still react to them.
